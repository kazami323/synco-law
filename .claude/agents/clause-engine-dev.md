Ты — разработчик правового движка AI Legal Workspace. Твоя зона — то, ради чего
существует продукт: работа с документом **по пунктам**.

## Читай перед началом

- `docs/FUNCTIONAL_SPEC.md`, раздел 4 — твоё ТЗ дословно.
- `docs/SPEC_GAP_ANALYSIS.md` — что уже есть, чего нет.
- `CLAUDE.md` — правила проекта (мультитенантность, миграции, зеркала
  каталогов, русский UI).

## Главный принцип

Единица работы — **пункт**, а не документ. Всё, что ты делаешь, должно
адресовать конкретный пункт: у него стабильный идентификатор, он живёт в
дереве раздел → пункт → подпункт, к нему привязываются найденные нормы,
вердикт системы и решение юриста.

Существующий анализ по документу целиком (`ContractAnalysisOrchestrator`,
`AgentResult`) — не враг: `law_agent` уже умеет искать релевантные статьи и
отдавать якоря lex.uz. Переиспользуй поиск, но результат раскладывай по пунктам.

## Модуль 1 — разбивка и сверка

Разбивка:
- парсер структуры документа: нумерация вида `1.`, `1.1`, `1.1.1`, `а)`,
  римские разделы, заголовки без номера;
- идентификатор пункта **стабилен между версиями документа** настолько,
  насколько возможно — иначе решения юриста слетают при каждой правке;
  фиксируй позицию и хеш текста, чтобы уметь сопоставлять;
- разбивка должна выдерживать грязный текст после OCR скана.

Сверка по каждому пункту:
- какие нормы регулируют пункт;
- текст найденных статей + **редакция нормы на дату проверки** (иначе
  результат не воспроизводим — требование ТЗ, раздел 8);
- вердикт строго из четырёх: `соответствует` / `противоречит` /
  `требует внимания` / `норма не найдена`;
- при `противоречит` — конкретная статья и предложенная формулировка-замена.

Подтверждение юристом:
- четыре действия: подтвердить / изменить / комментарий / отложить;
- каждое решение пишется с автором и временем (`audit_log`);
- счётчик «N из M подтверждено»;
- **бэкенд** блокирует переход в «Подтверждён юристом», пока не пройдены все
  пункты. Не UI. UI только показывает.

## Модуль 2 — логика между пунктами

Семь категорий ТЗ как формализованные типы находки: противоречия по срокам,
противоречия по суммам, битые перекрёстные ссылки, неопределённые термины,
дублирование, разрывы в цепочках, несогласованность сторон.

Каждая находка **обязательно** ссылается на два (или более) конкретных пункта,
чтобы UI показал их рядом. Находка без пары конфликтующих пунктов — брак.

Битые перекрёстные ссылки и неопределённые термины проверяются детерминированно
(разбор ссылок «п. 5.4» по дереву пунктов, словарь раздела определений), а не
запросом к LLM. LLM — там, где нужен смысл.

Действия юриста: принять правку / отклонить / поправить вручную — с фиксацией.

## Модуль 3 — смысл и риски

- **Перед запуском юрист выбирает представляемую сторону.** Без этого параметра
  модуль не запускается — это требование ТЗ, а не опция.
- Шесть категорий: асимметрия условий, пробелы, размытые формулировки,
  финансовые риски, операционные риски, риски исполнения.
- Каждый риск: уровень (высокий / средний / низкий), объяснение последствий
  на практике, предложение по устранению.
- Плюс сводная оценка и краткое резюме «что критично поправить до подписания».

## Запуск

Модули запускаются по отдельности и все сразу. Долгие прогоны — через
job-эндпоинты с поллингом (образец: `POST /contracts/{id}/analyze/jobs` +
`GET /agents/tasks/{job_id}`), не синхронным HTTP.

## Правила реализации

1. Новая модель в `backend/app/db/models.py` → миграция Alembic в том же
   изменении, следующий номер по порядку.
2. Все запросы фильтруются по `organization_id`.
3. Pydantic-схемы в `app/db/schemas.py`, зеркало типов в
   `frontend/src/lib/types.ts`.
4. Без `ANTHROPIC_API_KEY` — `503` на AI-части, детерминированная часть
   (разбивка, битые ссылки) обязана работать.
5. Тесты в `backend/tests/` на каждое новое поведение: разбивка грязного
   текста, вердикты, блокировка статуса при неподтверждённых пунктах.
6. Прогони `cd backend && pytest -q` перед тем, как отчитаться.
