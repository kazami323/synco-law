## 2. Статусы документа — ✅

`ContractStatus` в [models.py](../backend/app/db/models.py), названия и правила —
[statuses.py](../backend/app/core/statuses.py), зеркало на фронте в
[contract-chips.tsx](../frontend/src/components/contract-chips.tsx).

| Статус ТЗ | Значение в БД | Кто ставит |
|---|---|---|
| Черновик | `draft` | система |
| Сгенерирован | `generated` | система |
| На проверке | `analyzing` | система (запуск модулей) |
| Проверен | `analyzed` | система (отработал хотя бы один модуль — ТЗ разрешает гонять их порознь) |
| Подтверждён юристом | `approved` | юрист (право `approve` есть и у рядового юриста, как в ТЗ) — **только после прохода по всем пунктам** |
| На доработке | `needs_revision` | юрист / руководитель |
| Финальный | `ready_to_sign` | старший юрист или руководитель (право `finalize`), редактирование заблокировано |
| В архиве | `archived` | юрист (право `archive`; `delete` осталось у администратора и означало бы настоящее удаление) |

Сверх ТЗ сохранены `approved_finance` и `signed` — финансовое согласование и
E-IMZO, надстройка проекта.

Блокирующие правила живут на бэкенде, а не в интерфейсе:

- `_ensure_clauses_confirmed` в [workflow.py](../backend/app/api/workflow.py) —
  переход в «Подтверждён юристом» отклоняется с 409, пока есть непройденные
  пункты;
- `_ensure_unlocked` в [contracts.py](../backend/app/api/contracts.py) — правка
  текста в «Финальном» отклоняется с 409;
- право `finalize` есть у `senior_lawyer`, `head` и `admin` — ТЗ (раздел 7)
  отдаёт «Финальный» одной строкой «Старший юрист / руководитель»;
- переход в «Финальный» возможен и напрямую из «Подтверждён юристом»:
  финансовое согласование добавлено сверх ТЗ, и в организации без сотрудника
  с ролью «финансы» документ иначе не доходил до «Финального» вообще;
- правка текста в `approved`/`approved_finance` возвращает документ в
  «На доработке»: иначе можно подтвердить одну редакцию и подписать другую.

## 3. Создание документа — ✅

### 3.1. Генерация с нуля

| Шаг | Реализация |
|---|---|
| Шаг 1 — каталог типов | [document_types.py](../backend/app/core/document_types.py): поставка, услуги, подряд, аренда, купля-продажа, трудовой, NDA, лицензионный, доп. соглашение + продукты работы юриста. Отдаётся через `GET /api/document-types` с обязательными блоками и правовыми ориентирами |
| Шаг 2 — шаблон | Выбор шаблона организации в мастере; `template_id` уходит в генерацию |
| Шаг 3 — постановка задачи | Текст или голос: [draft-task-input.tsx](../frontend/src/components/draft-task-input.tsx) |
| Шаг 3 — карточка параметров | `POST /api/agents/draft/extract-params` → редактируемая карточка (стороны, суммы, сроки, санкции, подсудность). **Генерация без разобранной карточки не запускается**: раньше кнопку можно было нажать сразу, и модель домысливала стороны, суммы и сроки, а юрист узнавал об этом из готового текста |
| Шаг 4 — генерация | `DraftAgent.create_contract` собирает документ из шаблона + подтверждённых параметров + контекста проекта + обязательных блоков типа |

**Ограничение по голосу:** расшифровка речи идёт средствами браузера
(Web Speech API, Chrome и Edge). Серверного STT в проекте нет — при
необходимости поддержки других браузеров нужно подключать внешний сервис
распознавания. В остальных браузерах кнопка микрофона скрыта, текстовый ввод
работает всегда.

### 3.2. Загрузка готового документа — ✅

DOCX / PDF / TXT, скан с OCR через Claude vision. Загруженный документ
разбирается на пункты **сразу при загрузке** — разбивка детерминированная и не
требует ни ключа API, ни токенов.

**Осознанное ограничение:** сами модули проверки автоматически не запускаются.
Модуль 3 без указанной стороны не имеет смысла, а тратить дневную квоту
токенов организации на каждую загрузку — решение юриста, а не системы.

### 3.3. Создание из существующего — ✅

`POST /api/contracts/{id}/duplicate`, кнопка «Создать копию». Результаты
проверок и решения юриста в копию **не** переносятся: это другой договор,
чужое подтверждение к нему не относится.

## 4. Модули проверки — ✅

Запускаются по отдельности или все сразу: `POST /api/contracts/{id}/review`
с `modules`. Каждый прогон — строка `review_runs` со своим статусом, поэтому
прогресс переживает перезапуск сервера.

### Модуль 1. Разбивка на пункты и сверка с правовой базой

- **Разбивка** — [clause_splitter.py](../backend/app/services/clause_splitter.py):
  детерминированная, без LLM. Понимает нумерацию `1.`, `1.1`, `1.1.1`,
  `а)`, римские разделы, «Раздел 3», капслок-заголовки; отбрасывает номера
  страниц и висячие переносы после OCR; при отсутствии нумерации режет по
  абзацам. Подпункт «а)» внутри 4.3 получает якорь `4.3.а`.
- **Стабильность якорей** — решение юриста переносится между версиями по
  якорю; если текст пункта изменился, подтверждение помечается устаревшим
  (`stale`) и пункт нужно пройти заново.
- **Сверка** — [clause_checker.py](../backend/app/agents/clause_checker.py):
  вердикт строго из четырёх (`соответствует` / `противоречит` /
  `требует внимания` / `норма не найдена`), с текстом статьи и **редакцией
  нормы на дату проверки** в снапшоте `clause_checks.sources`.
- **Защита от выдуманных норм**: вердикт «противоречит» без подтверждённого
  источника из локальной базы автоматически понижается до «требует внимания»
  с честной пометкой.
- **Подтверждение юристом** — четыре действия (подтвердить / изменить /
  комментарий / отложить), каждое пишется с автором и временем в
  `clause_decisions` и `audit_log`. Счётчик «N из M».
- **Интерфейс** — [clause-review.tsx](../frontend/src/components/review/clause-review.tsx):
  слева текст пункта, справа нормы и вердикт.

### Модуль 2. Сверка логики между пунктами

Семь категорий ТЗ. Три считаются кодом
([logic_check.py](../backend/app/services/logic_check.py)), четыре — моделью
([logic_agent.py](../backend/app/agents/logic_agent.py)):

| Категория | Как ищется |
|---|---|
| Битые перекрёстные ссылки | код: разбор ссылок по дереву якорей |
| Несогласованность сторон | код: сравнение обозначений в шапке и в тексте |
| Неопределённые термины | код: термины в кавычках против раздела определений |
| Противоречия по срокам / суммам, дублирование, разрывы в цепочках | LLM |

Находка без **двух** конкретных пунктов отбрасывается — ТЗ обещает показать
конфликтующие пункты рядом, и интерфейс их так и показывает. Детерминированная
часть работает и при недоступном AI.

### Модуль 3. Сверка на смысл и риски

- **Сторона обязательна**: запуск без `party_side` отклоняется с 400.
- Шесть категорий ТЗ (асимметрия, пробелы, размытые формулировки, финансовые,
  операционные, риски исполнения), уровень высокий/средний/низкий, последствия
  на практике и предложение по устранению — `RiskFinding`.
- Отсутствие обязательных блоков типа документа подсказывается модели как
  категория «пробелы».

## 6. База шаблонов — ✅

`DocumentTemplate`, [templates.py](../backend/app/api/templates.py), раздел
«Шаблоны» в интерфейсе:

- шаблоны по типам документов;
- дата актуализации;
- отметка «верифицирован» с указанием юриста (право `verify_template`);
- сохранение подтверждённого документа как шаблона —
  `POST /api/contracts/{id}/save-as-template`, только из статусов от
  «Подтверждён юристом» и выше;
- при изменении законодательства
  [legal_refresh](../backend/app/services/legal_refresh.py) снимает
  верификацию со всех шаблонов, ставит причину и шлёт уведомление авторам.

**Осознанное решение:** связать конкретный шаблон с конкретной изменившейся
статьёй надёжно нельзя, поэтому помечаются все верифицированные шаблоны.
Ложное «перепроверьте» стоит юристу десяти минут, пропущенное изменение
закона — недействительного условия в договоре.

## Что осталось и осознанные ограничения

1. **Гейт по пунктам включается, когда документ разобран на пункты.**
   Загруженные документы (3.2) разбираются сразу, поэтому правило на них
   действует. Документ, заведённый вставкой текста и ни разу не открытый в
   правовом движке, пунктов не имеет и идёт прежним маршрутом согласования.
   Чтобы правило действовало всегда, разбивку надо делать и при создании
   из текста — это решение заказчика, а не техническое ограничение.

2. **Модули проверки не запускаются автоматически.** ТЗ (3.2) говорит
   «переводит документ сразу в очередь проверки». Разбивка делается сразу,
   а запуск модулей оставлен юристу: Модуль 3 без указанной стороны не имеет
   смысла, а тратить дневную квоту токенов организации на каждую загрузку —
   решение юриста, а не системы.

3. **Голос — на стороне браузера** (Chrome/Edge). Серверное распознавание
   потребует внешнего STT-сервиса.

4. **Судебная практика** в правовой базе не заведена.

5. **Каталог типов документов** редактируется в коде
   (`document_types.py` + зеркало на фронте), а не из интерфейса
   администратора. Право `manage_catalog` заведено, экрана пока нет.

6. **Локальный прогон тестов на машине разработчика невозможен**: политика
   Windows App Control блокирует нативные бинарники (`pydantic_core`).
   Backend-тесты гоняются в контейнере (`docker compose exec backend pytest`)
   и в CI; фронтенд собирается и линтуется локально.
